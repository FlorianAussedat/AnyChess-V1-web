# AnyChess 0.0.7 — PR 04 : Import / Export PGN, FEN et fichiers

## Git et périmètre

- Source et cible : `feature/0.0.7-reglages-difficultes`, PR #122, commit `29769b3bcabccc2ff18800b3ccd92dce2c16c51e`.
- Travail : `feature/0.0.7-import-export-pgn-fen` ; PR brouillon empilée contenant uniquement PR 04.
- Aucun APK, aucune dépendance ajoutée, aucun backend modifié, aucune fusion. PR 05 non commencée.
- Les adaptations des contexts Classic/Ouvertures concernent uniquement leurs callbacks d'export. Réglages, difficultés, navigation générale, profil, avatar et authentification restent inchangés.

## Causes exactes

1. `downloadPgnFile` était une fonction DOM synchrone sans résultat : sur Android, `document` absent provoquait un retour immédiat. AnyLyseur annonçait néanmoins une réussite juste après l'appel.
2. La modale Classic/Ouvertures ne sollicitait même pas ce callback sur Android : elle tentait `navigator.clipboard`, généralement absent, puis fermait la modale sans résultat.
3. AnyLyseur utilisait cette même fonction pour `position.fen`, qui ajoutait `.pgn`. L'export FEN suit désormais une voie explicitement typée FEN ; il utilise la position réellement présentée sur l'échiquier, y compris la prévisualisation, plutôt qu'une position de départ fixe.
4. `PgnImportPanel.ingestFiles` ne préparait que `files[0]`, malgré un sélecteur multiple. Les sélecteurs ignoraient aussi les exceptions de lecture et pouvaient présenter un lot entièrement illisible comme une annulation.
5. La lecture native reposait sur `fetch(uri)`, qui n'est pas un lecteur Android fiable de `content://` et `file://`. La copie locale du DocumentPicker est désormais lue avec l'API native de fichiers, sans requête réseau de l'application.
6. L'export enrichi omettait les commentaires avant les coups et plusieurs tags ; son placement des variantes de premier coup après toute la ligne principale pouvait produire une réimportation illégale. Il supprimait aussi des annotations originales même sans valeur de remplacement.
7. L'export de la partie d'ouverture ne conservait que la ligne jouée. Les alternatives du document source aux positions atteintes sont désormais conservées comme variantes, sans coller leurs commentaires à la ligne jouée ni changer les coups effectivement joués.
8. Le générateur linéaire numérotait toujours à partir de `1.` et supposait les Blancs au trait. Il utilise désormais les FEN précédant les coups et ajoute SetUp/FEN si la position initiale est particulière.
9. Le sélecteur de parties annonçait toujours une limite de dix, même dans un contexte autorisant cent parties ou une seule. La limite affichée et annoncée correspond maintenant au parcours.

## Contrat des fichiers et limites

- Résultats de transfert : `saved`, `downloadStarted`, `copied`, `sharedText`, `cancelled`, `unavailable`, `failed`, `busy`.
- `saved` n'est retourné qu'après résolution de l'écriture SAF. L'ouverture d'une fenêtre de partage ne produit pas ce résultat. Android peut renvoyer « partagé » même si l'utilisateur ferme certaines applications de partage : le message indique seulement la remise du texte au système.
- Le navigateur peut confirmer le déclenchement d'un téléchargement, pas son enregistrement final sur disque : message spécifique `downloadStarted`.
- Extension `.pgn` ou `.fen` normalisée, nom nettoyé, MIME propre au format. L'URL Blob Web est libérée après consommation, pas immédiatement avant que le navigateur puisse l'utiliser.
- SAF crée un nouveau document dans le dossier choisi. Si son écriture échoue, seule cette nouvelle URI est proposée au nettoyage ; aucun PGN existant n'est supprimé par l'export.
- Au-delà de dix fichiers, seul leur inventaire est préparé ; l'utilisateur choisit lesquels lire. La résolution refuse plus de dix identifiants au lieu de tronquer le lot.
- Limite de 8 Mio annoncés par fichier et de 16 Mio de caractères conservés pour un lot ; taille vérifiée avant lecture lorsqu'elle est fournie par le sélecteur ou le système, puis après lecture. Lecture séquentielle. Un dépassement produit un diagnostic nommé, jamais une annulation fictive.
- Les fichiers sont indexés indépendamment avant concaténation : deux fichiers sans en-têtes ne peuvent pas être confondus en une seule partie. Les slices gardent leurs offsets et noms sources.
- Une partie est légalisée avec le parseur Reader avant son chargement/import. Une partie invalide n'écarte pas les autres parties sélectionnées. Les échecs de lecture et de destination apparaissent dans le bilan avec les fichiers concernés.
- Les collisions de noms d'ouvertures suivent la règle existante de suffixe ; elles créent une nouvelle entrée avec un nouvel identifiant. Une étude existante sauvegardée reste identifiée par son ID. Une erreur d'écriture locale rétablit l'état précédent de l'import/remplacement concerné, sans supprimer les autres fichiers.
- Les commentaires et tags de l'auteur sont conservés ; les évaluations sont ajoutées selon l'option. Les tags d'évaluation originaux ne sont remplacés que lorsqu'une nouvelle valeur existe. Les SAN restent anglais/standards indépendamment de FR/EN.

## Capacités Android : ce qui est vérifié et ce qui reste conditionnel

Le dépôt utilise Expo SDK 54 et son verrouillage inclut déjà `expo-file-system` 19.0.23 comme dépendance transitive d'Expo. Aucune dépendance n'est ajoutée. Les noms et signatures du module natif sont vérifiés contre le code SDK installé :

- `requireOptionalNativeModule('ExponentFileSystem')` ;
- SAF : `requestDirectoryPermissionsAsync`, `createSAFFileAsync`, `writeAsStringAsync` ;
- lecture locale : `readAsStringAsync`, avec `getInfoAsync` optionnel ;
- suppression d'un nouveau document incomplet : `deleteAsync` optionnel ;
- partage texte : `Share.share` de React Native ; copie : helper AnyChess existant basé notamment sur `expo-clipboard`.

La présence effective de ces méthodes dans **l'APK déjà installé sur le Pixel n'est pas observable depuis Codex**. Elle est sondée au moment de l'action. Si les API SAF manquent, l'enregistrement renvoie `unavailable`, explique le module requis et laisse copier ou partager le texte. Le partage texte ne requiert pas `expo-sharing`, qui n'est pas ajouté. Si l'API native de lecture manque et que le sélecteur n'expose pas `File.text`, l'import de fichier est signalé illisible ; le collage PGN reste utilisable.

Un client dépourvu d'ExponentFileSystem nécessiterait ultérieurement une reconstruction incluant ce module pour enregistrer/lire de vrais fichiers ; aucun build natif n'est lancé ici. Les tests et l'export JavaScript ne prouvent pas la présence d'un module dans ce client installé.

Pour Drive, `copyToCacheDirectory: true` demande au fournisseur Android une copie locale. Drive peut devoir télécharger un fichier non disponible hors ligne : cela relève du fournisseur. Une fois copié, AnyChess lit le cache sans réseau ; un fichier déjà local ne dépend d'aucun service Supabase.
