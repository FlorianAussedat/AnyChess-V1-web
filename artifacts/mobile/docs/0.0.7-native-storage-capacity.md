# Quota natif Android — correction après #130

Base : #130, `ee875f7cc7c0ccab5a1f0481ea215f4ab0b51c3b`.
Branche : `fix/0.0.7-native-storage-capacity`, cible `fix/0.0.7-restauration-stockage`.

## Preuves et limites

Les mesures Pixel fournies sont : 6 046 Kio physiques de valeurs, onze sauvegardes
(5 475 Kio), pool partagé vide, un workspace, 94 blocs dont 90 référencés et quatre
candidats, aucune racine invalide ou ligne illisible. Dernier refus :
`storage.pool.block_write`, `local_quota`, file de traduction, 213 Kio logiques.

Le code natif installé de `@react-native-async-storage/async-storage` **2.2.0**
établit la chaîne suivante :

1. `android/config.gradle`, `getDatabaseSize()` : **6L** par défaut ; lecture de
   `rootProject.properties['AsyncStorage_db_size_in_MB']` si entier valide.
2. `android/build.gradle` : génération de `BuildConfig.AsyncStorage_db_size`
   comme Long à partir de cette valeur.
3. `ReactDatabaseSupplier.java` : multiplication par `1024L * 1024L`, puis
   `mDb.setMaximumSize(mMaximumDatabaseSize)` lors de l'ouverture de la base.
4. `AsyncStorage_useNextStorage` vaut false par défaut. `newArchEnabled=true`
   ne signifie pas activation du moteur expérimental Room : le module Java
   classique et son fournisseur SQLite restent concernés.

Le dépôt et les profils EAS ne définissaient aucune augmentation. Le plafond
attendu d'une compilation non surchargée est donc **6 Mio = 6 144 Kio**.
Les valeurs physiques mesurées excluent pages, index, métadonnées et journal
SQLite : la marge réelle est inférieure aux 98 Kio apparents. Les 213 Kio de
l'erreur décrivent la valeur logique, pas nécessairement la taille physique du
bloc refusé. Le découpage corrige les lignes volumineuses, pas la capacité totale.

Le pool nul ne prouve pas l'absence du nouveau lecteur : il est compatible avec
un premier bloc refusé faute d'espace, alors que les sauvegardes héritées occupent
la base. La limite empêche aussi la création temporaire nécessaire à une conversion
sûre : on ne peut pas compresser en supprimant d'abord la seule copie source.

**Limite de preuve :** aucun APK/DEX installé, paramètre distant EAS ou
`PRAGMA max_page_count` du Pixel n'a été inspecté. La chaîne native et la
reproduction démontrent cette cause pour le build issu de la configuration du
dépôt ; un override externe ou une saturation du disque restent à exclure sur
l'appareil. Aucun test simulé n'est présenté comme une inspection de son binaire.

## Correction

Le plugin Expo `withAsyncStorageCapacity.js` inscrit de façon idempotente
`AsyncStorage_db_size_in_MB=32` dans les propriétés Gradle **Dev et Preview
uniquement**. Il remplace les doublons de cette seule propriété, conserve les
autres et ne s'applique pas à Stable/standalone. Ce plafond de 32 Mio apporte de
la place temporaire pour les données actives et la récupération ; il ne réserve
pas immédiatement 32 Mio et ne garantit pas une capacité illimitée.

Le package, la signature, la base et son schéma ne changent pas. Aucun clear,
reset, changement de version de base, suppression de racine ou migration cloud.
Les limites de taille de ligne/CursorWindow ne sont pas relevées : les blocs de
#130 restent nécessaires. Une erreur réelle de quota continue à suspendre les
reprises automatiques, sans annoncer un succès.

Preview passe de **versionCode 2 à 3** pour la prochaine mise à jour Android.
Dev conserve son identité et son versionCode ; les deux applications ont besoin
d'une **nouvelle compilation native autorisée séparément** pour bénéficier du
plafond. Metro seul ne peut pas modifier le `BuildConfig` de l'APK installée.
EAS, les signatures et les configurations Supabase/Netlify sont inchangés.

## Sauvegardes et conversion progressive

Aucune nouvelle conversion générale n'est lancée au démarrage ou en arrière-plan.
Les onze sauvegardes héritées restent lisibles et utilisables sans conversion.
Le réemploi d'une sauvegarde identique vérifiée par #130 reste inchangé.

Le primitive existant `compactItem()` peut traiter un état à la fois une fois la
marge restaurée : lire tous les chunks, écrire les références/blocs compressés,
relire et comparer exactement le contenu logique, puis seulement retirer les
anciens chunks engagés de **cette même racine** dont le remplacement est vérifié.
Aucun état unique ni bloc ambigu/orphelin ne peut être supprimé sur son âge ou son
nom. Les tests vérifient onze racines inchangées logiquement, redémarrage entre
conversions, absence de croissance lors d'une deuxième passe et conservation des
quatre candidats. Les tests hérités couvrent aussi interruption et publication
ambiguë. Une éventuelle action utilisateur de conversion complète reste un travail
séparé : cette PR ne déclenche aucun nettoyage sur le Pixel.
