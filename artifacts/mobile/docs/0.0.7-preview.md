# AnyChess Preview 0.0.7 — préparation sans APK ni déploiement

Base : `fix/0.0.7-asyncstorage-quota`, PR #128, commit `7ad2488b9ac44b311f734c8f4e301e0294eb268a`.
Branche : `feature/0.0.7-preview`. Cible : `fix/0.0.7-asyncstorage-quota`.

## Architecture confirmée

**Un seul projet Supabase et un seul site Netlify pour toutes les variantes.** Aucun deuxième projet, base Preview ou environnement cloud de démonstration créé. Le même compte retrouve les documents synchronisés dans les versions compatibles. Utiliser un compte de test dédié dans le projet commun pour la première recette, jamais la seule copie de données personnelles.

| Variante | Package | Schéma | Client page e-mail |
| --- | --- | --- | --- |
| Dev | `com.anychess.dev` | `anychessdev` | `dev` (intent historique `exp+anychessdev`) |
| Preview | `com.anychess.preview` | `anychesspreview` | `preview` |
| Stable | `com.anychess.app` | `mobile` | `app` |
| Standalone historique | `com.anychess.standalone` | `anychess` | `standalone` sur la page ; replis historiques inchangés |

Android sépare les données locales par package, pas les données cloud : supprimer le compte commun affecterait toutes les variantes. Aucun import implicite des espaces locaux des autres installations.

## Réalisation

- Variante Expo explicite : AnyChess Preview / 0.0.7 / versionCode initial 1.
- Profil EAS Preview, environnement `preview`, distribution interne, APK Release arm64-v8a, `developmentClient: false`, credentials distants. Ni plugin ni modules Dev Client ; nettoyage des schémas `exp+…`. Aucun Metro requis à l'utilisation, aucun nouveau système OTA ni module natif.
- Signature Preview séparée : nouveau plugin qui ne charge jamais `.signing/release.env`. EAS doit injecter une nouvelle clé persistante pour `com.anychess.preview`. Un garde Gradle lors des tâches Release refuse le mauvais package, la signature debug et les certificats publics connus Stable/standalone. L'intégration EAS/Gradle reste à valider lors d'un futur build natif ; aucun garde historique n'est contourné.
- Association EAS uniquement pour Preview via `ANYCHESS_PREVIEW_EAS_OWNER` et `ANYCHESS_PREVIEW_EAS_PROJECT_ID` (UUID). Pas d'identité fictive enregistrée ni de `eas init` exécuté. Le contrôle EAS bloque tant qu'ils manquent.
- Script `preview:check` en lecture seule. Hook `eas-build-post-install` : contrôle Preview uniquement, sans effet sur les anciens profils. Le script local APK Dev/Stable indique la procédure EAS Preview au lieu d'essayer de lui générer une clé Stable.
- Avant bundling Preview, Metro refuse mauvais projet/client, clé serveur, JWT anon expiré ou d'un autre projet et variable publique supplémentaire non prévue. Pas de récupération silencieuse depuis un autre environnement. Ce contrôle lit les déclarations du JWT, sans vérification cryptographique ou distante.
- Preview reconnu dans le constructeur Auth, les interpréteurs, relais, liens Android et nettoyage des paramètres. Retour strict `intent://utilisateur#Intent;scheme=anychesspreview;package=com.anychess.preview;end` ou `anychesspreview://utilisateur`. Aucun token dans le retour vers l'app.
- Le lien statique historique est masqué jusqu'à sélection du client par JavaScript pour ne pas proposer standalone lors d'un chargement Preview interrompu. Après initialisation, destinations historiques identiques.
- Sources, artefact suivi `site/auth/confirm.html` et sortie locale `dist/confirm-site` cohérents. Le site réel utilise le générateur `scripts/build-confirm-site.mjs` défini dans `netlify.toml`. Aucune publication.

## Paramètres publics communs

Fournir dans l'environnement EAS `preview` : `EXPO_PUBLIC_SUPABASE_URL` et `EXPO_PUBLIC_SUPABASE_ANON_KEY`, **les mêmes valeurs publiques que Dev/Stable/standalone**. Les deux champs existent dans le `.env` local ignoré ; contrôle du projet, rôle anon et expiration réussi sans afficher la clé. La récupération publique depuis l'APK V0.0.6 existe dans le dépôt, mais Preview ne la recopie pas automatiquement lors du bundle.

Le profil fixe déjà `EXPO_PUBLIC_APP_CLIENT=preview` et `EXPO_PUBLIC_AUTH_CONFIRM_URL=https://sparkly-paprenjak-65f499.netlify.app/auth/confirm`. Preview accepte uniquement ces quatre variables publiques. Les variables non publiques d'association EAS servent à résoudre sa configuration. Les références statiques `EXPO_PUBLIC_*` permettent l'intégration par Expo ; ne pas compter sur les seuls alias `ANYCHESS_SUPABASE_*`.

Ne jamais fournir service_role, clé DeepL, mot de passe, jeton administrateur ou signature existante comme variable publique. Les secrets restent côté serveur. Aucun ajout à `extra`, au manifeste ou aux liens. Vérifier aussi l'archive EAS et le bundle final avant distribution : un fichier secret ne doit pas être envoyé simplement parce qu'il n'est pas importé.

## Compatibilité interversions

Le moteur, les 18 clés et les formats de synchronisation ne sont pas modifiés. Les tests utilisent deux moteurs complets et deux stockages locaux indépendants avec le véritable adaptateur REST `SupabaseCloudRemote`, un propriétaire commun et un serveur HTTP simulé en mémoire avec contrôle de révision. Aucun socket ou compte distant réel.

Vérifié : créations distinctes portant le même nom, dossiers imbriqués, variantes/commentaires/NAG, échanges dans les deux sens, profil/langue/records, édition hors ligne conservée après redémarrage puis reprise en données mobiles, identifiants stables et absence de nouvelle copie lors de synchronisations répétées.

**Limite existante démontrée :** deux contenus PGN différents pour le même identifiant produisent une copie de récupération stable, y compris après certaines éditions successives. La fusion conservatrice ne distingue pas toujours ancien contenu et conflit simultané. Les tests contrôlent les contenus, le nombre et la stabilité de ces copies. Une exigence stricte de zéro copie après édition nécessiterait un chantier séparé ; aucune modification du moteur de fusion dans cette PR.

**Anciens clients : utilisation simultanée non validée et déconseillée sur un compte réel.** Un ancien upsert inconditionnel peut écraser le document distant même si `revision` existe. Un test démontre ce risque en mémoire. La colonne seule ne garantit pas un CAS universel et il n'existe pas de transaction couvrant les 18 documents. Identifier le code/protocole des APK réellement installées avant usage croisé. Les snapshots PR #127/#128 sont locaux et ne transitent pas entre packages.

### Catégories synchronisées et exclusions

18 documents inchangés : répertoires, bibliothèque de parties/analyses, traductions des commentaires PGN, file de traduction, maîtrise des lignes d'ouverture, préférences FR/EN/difficultés, profil, records quiz d'ouvertures, records nommage des coups, records jeu de coups, records mémoire à l'aveugle, historique tactique, séries tactiques, historique culture, retours culture, finales/Défends la nulle, finales théoriques, lignes récentes Continuer la ligne.

Photo avatar : canal Storage séparé `avatars/<userId>/avatar.png`, cache et intention locale par compte. Mascotte : identifiant stable dans le profil, images embarquées.

**Non synchronisés :** sessions de jeu/activité/lecteur/AnyLyseur en cours, navigation/modales/dossiers dépliés, caches moteur/images/catalogues/modèles téléchargés, historique absent de la liste des 18 clés, sauvegardes/index/espaces de récupération, espaces et coffre invités, intention avatar avant transfert, jetons/session d'authentification, e-mail mémorisé et réglages propres à l'appareil. Une partie en cours n'est partagée que si elle est enregistrée dans une catégorie synchronisée. Pas de restriction Wi-Fi réintroduite.

## Construction future — après autorisation explicite

Les commandes suivantes ne sont pas exécutées pour construire une APK pendant cette tâche.

1. Relire cette PR et ses blocages. Arrêter si schéma/protocole, liens Auth ou signature ne sont pas prêts.
2. Depuis `artifacts/mobile`, utiliser Node/pnpm et CLI EAS sur une machine autorisée ; se connecter au compte choisi. Autoriser séparément la création/liaison de projet si nécessaire. Contrôler UUID, propriétaire et slug avant toute opération distante.
3. Configurer l'environnement EAS `preview` : deux variables publiques Supabase existantes et `ANYCHESS_PREVIEW_EAS_OWNER` / `ANYCHESS_PREVIEW_EAS_PROJECT_ID`. Les variables publiques doivent être accessibles pendant le bundling ; ne pas transmettre de secrets serveur ou copier un `.env` backend.
4. Rendre UUID/owner disponibles dans le shell local. Lancer `node scripts/check-preview-build.mjs --local --require-eas`. Contrôle en lecture seule, sans certifier les droits distants.
5. Vérifier `ANYCHESS_VARIANT=preview pnpm exec expo config --type public`, sans publier son résultat intégral. Contrôler nom, package, schéma, projet. Le bundling exigera également les valeurs publiques et le client/URL Auth du profil. Aucun prebuild nécessaire pour cette inspection.
6. Seulement après autorisation : `pnpm exec eas build --platform android --profile preview`. EAS utilise les credentials distants propres à Preview ; ne pas sélectionner une clé d'une autre application. Le hook contrôle les valeurs et l'association ; les plugins retirent Dev Client et le garde Gradle refuse les signatures interdites.
7. Si le garde échoue, inspecter l'injection EAS/Gradle, sans le désactiver. Le script local APK Dev/Stable ne construit pas Preview et n'en génère pas la clé.
8. Stockfish : téléchargement officiel arm64 au preBuild et SHA-256 inchangés, module UCI, extraction native et licence/sources conservés. Vérifier accès à l'archive et inclusion du binaire. Un export JavaScript ne prouve pas son fonctionnement Android.
9. Inspecter APK/manifeste/certificat/bundle : bon package, pas de lanceur/modules Dev Client, aucun secret serveur, assets natifs présents. Installer sans désinstaller les autres variantes, sans migration/import/nettoyage implicite de leurs données.
