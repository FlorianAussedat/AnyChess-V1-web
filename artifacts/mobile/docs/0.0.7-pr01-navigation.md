# 0.0.7 — PR 01 : Navigation et menus

Base auditée : `major-update/0.0.7`, commit `c8a45bff2945127737a105bdeae0cd30b471df54`.
Branche : `feature/0.0.7-navigation-menus`. Cible de la PR brouillon : `major-update/0.0.7`.

## Audit avant modification

Le layout racine utilise Expo Router 6 et un `Stack` sans en-tête natif.
Les répertoires openings, parties, puzzles, visualisation et quiz-ouverture ont
leur propre layout Stack. Les providers de jeu sont locaux aux routes ; ils ne
doivent pas être déplacés dans un provider global ou un deuxième routeur.

Les quatre écrans principaux sont `/`, `/records`, `/utilisateur`, `/parametres`.
Ils ne correspondent pas aux familles d'activités de l'accueil.

| Entrée | Routes secondaires / destinations |
| --- | --- |
| Accueil | `/classic`, `/blind`, `/openings`, `/parties`, `/puzzles`, `/visualisation`, `/quiz-ouverture` |
| Ouvertures | `/openings/learn`, `manage`, `import`, `[folderId]`, `study`, `annotate`, `continue`, `play` |
| Parties | `/parties/import`, `/parties/analyzer`, `/parties/[gameId]` (redirection compatible vers analyzer) |
| Exercices | `/puzzles/records`, `defends-nulle`, `defends-nulle-play`, `defends-nulle-history`, `defends-nulle-favorites`, `finales-theoriques`, `finales-theoriques-play` |
| Vision | `/visualisation/nommer`, `jouer`, `mental`, `records` |
| Culture | `/quiz-ouverture/quelle`, `culture` |
| Utilisateur | `/creer-compte`, répertoires, records, édition de profil en modales ; `CloudAccountSection` contient connexion et compte |
| Paramètres | Réglages en modales, lien invité vers Utilisateur ; aucune nouvelle route de réglage |
| Compatibilité / développement | `/profil` redirige vers Utilisateur ; `/open`, `+native-intent`, `+not-found`, `/dev/voice-parser`, `/dev/stockfish-uci` |

`/blind` et `/puzzles` contiennent plusieurs étapes dans une même route : hub,
réglages, activité et résultats. Les retours internes doivent continuer à utiliser
leurs callbacks de contexte, plutôt que dépiler la route à chaque étape.
La bibliothèque de parties possède également une pile de dossiers interne.

Constats :

- La barre était montée sur toutes les routes après préparation de l'application.
  Le padding de sa hauteur était systématique. Son rendu absolu ne réservait pas
  lui-même l'inset inférieur. Les préfixes records/profil pouvaient activer un onglet
  sur un écran secondaire.
- Records, Utilisateur et Paramètres utilisaient `push` entre écrans principaux.
  Des alternances répétées allongeaient l'historique.
- Le retour classique, plusieurs sélections Vision/Culture et l'entraînement aux
  ouvertures forçaient l'accueil ou un hub, même avec un historique utile.
  L'analyseur privilégiait `/parties` au lieu de l'écran appelant.
- Beaucoup de retours passifs utilisaient `router.back()` sans repli en accès direct.
  PuzzleHub avait même un repli vers sa propre route.
- Les confirmations d'activité sont centralisées dans `useActiveSessionBack`,
  `confirmActiveSessionBack`, `confirmLeaveToHub` et `endActivity` ; les sessions
  sont enregistrées par `usePersistedActivity` / ActivitySessionsStore.
  Les callbacks de nettoyage doivent être conservés.
- L'éditeur PGN possède déjà son dialogue enregistrer/quitter/continuer et vide
  le brouillon de commentaire dans la session avant de décider s'il peut sortir.
  L'analyseur persiste la position et l'aller-retour avec l'éditeur est spécifique.
  Le bouton Android n'appelait pas systématiquement ces chemins d'en-tête.
- Aucun menu général partagé n'était présent. Connexion et compte existent déjà
  dans Utilisateur ; Paramètres conserve sa passerelle de connexion invitée.

## Décisions et périmètre

`NavigationShell` est l'unique propriétaire de la visibilité et du placement de
la barre. La politique des routes exige une correspondance exacte avec les quatre
écrans principaux et la fin du splash. La barre occupe une place normale dans le
layout, avec les insets inférieurs et latéraux ; aucun padding de barre n'est
ajouté au contenu, ni sur les sous-écrans ni pendant l'intro.

Les onglets utilisent `replace` entre écrans principaux. Un appui sur l'onglet
déjà actif ne fait rien. L'historique antérieur au groupe d'écrans principaux est
conservé, tandis que les visites successives des onglets ne s'empilent pas.
Les états de présentation locaux d'un écran principal peuvent être réinitialisés
à sa prochaine visite ; les données persistées ne sont pas modifiées.

`useSmartBack` est réutilisé et étendu : historique réel en priorité, puis repli
vers la famille appropriée. Les `ScreenHeader` passifs héritent de ce comportement.
Les callbacks explicites restent prioritaires pour les étapes internes, dossiers,
confirmations, annulations, sauvegardes et nettoyages.
`useHeaderHardwareBack` relie Android au callback exact de l'en-tête visible.
Les retours de routes d'activités dédiées utilisent désormais l'historique après
leur logique d'abandon existante. Un abandon qui revenait à une sélection interne
continue à le faire.

Sur le Web, `useWebNavigationGuard` intercepte `beforeRemove` pour une activité
active ou un éditeur modifié et appelle le même dialogue existant. Après une
confirmation ou une sauvegarde réussie, la suppression de route est autorisée
sans boucle de confirmation. Cela concerne la navigation dans l'application,
pas la fermeture forcée ou le rechargement du navigateur.

`GeneralMenu` apparaît en haut à droite des quatre écrans principaux, avec une
cible tactile issue des design tokens. Il utilise `AppDialogHost` et propose
une seule destination Utilisateur/Connexion ou Utilisateur/Mon compte, ainsi que
Paramètres. Il ne recopie pas les quatre onglets. L'écran Utilisateur conserve
ses deux branches et leur `CloudAccountSection`. Aucune authentification n'est
réimplémentée. Trois clés FR/EN décrivent le nouveau menu.

Les six PR suivantes ne sont pas implémentées ici. Les sujets de profil, réglages,
données/PGN, activités/quiz et moteurs restent indépendants ; les écrans existants
ne reçoivent que des adaptations de navigation. La PR 06 pourra faire évoluer
le compte derrière les mêmes destinations. Le détail des cinq autres PR n'a pas
été fourni : cette PR ne leur attribue pas de nouveaux objectifs produit.
Aucune configuration Supabase, clé, donnée utilisateur, bibliothèque PGN,
sauvegarde, règle de quiz ou force Stockfish n'est modifiée.

## Validation et commandes

Les dépendances présentes ont été utilisées sans installation. Le lanceur pnpm
de cet environnement tente une installation automatique dans un répertoire non
accessible ; les scripts du package ont donc été exécutés directement avec Node.

```sh
# Depuis la racine : typage mobile et bibliothèques
node node_modules/typescript/bin/tsc -p artifacts/mobile/tsconfig.json --noEmit
node node_modules/typescript/bin/tsc --build

# Depuis artifacts/mobile : les nouveaux tests (également dans le script test)
node --experimental-strip-types --import ./scripts/register-tsx-loader.mjs --test lib/navigation/__tests__/navigation.test.tsx

# Suite complète : exécuter la valeur scripts.test du package mobile.
# Export Web hors ligne, sans serveur ni APK :
EXPO_NO_TELEMETRY=1 EXPO_OFFLINE=1 __UNSAFE_EXPO_HOME_DIRECTORY=/tmp/anychess-expo-state node node_modules/expo/bin/cli export --platform web --output-dir /tmp/anychess-navigation-web
```

Les nouveaux tests montent les composants et hooks réels avec les adaptateurs
Expo/React Native et l'état de compte simulés. Ils couvrent les routes énumérées
depuis le dossier app, la visibilité au splash, l'absence d'espace réservé,
l'onglet actif, les appuis répétés, le vrai `StackRouter` React Navigation,
les retours imbriqués et directs, Android, l'éditeur, les suppressions de route
Web, les confirmations/cancellations et la conservation du stockage, puis les
menus invités/connectés en FR/EN. Les tests de structure existants sont adaptés
pour vérifier la délégation au retour commun au lieu d'exiger un appel dupliqué.

Avant modification, la suite renvoyait 190 fichiers tests réussis sur 193, avec :

- `whitePerspective.engine.test.ts` : démarrage Stockfish dépassé (45 secondes).
- `postGameGrade.engine.test.ts` : démarrage Stockfish dépassé (15 secondes).
- `authFlow.test.ts` : le serveur du scénario de confirmation est refusé par le
  bac à sable (`listen EPERM 0.0.0.0`). Les autres scénarios de ce fichier passent.

Ces échecs sont reproduits sur la base avant modification ; ils ne sont pas
assimilés au précédent résultat rapporté de 1 échec sur 1 737 assertions.
Le runner de cette session affiche le nombre de fichiers tests, pas ce total
historique d'assertions.

Résultat final : **191 fichiers tests réussis sur 194**, avec les trois mêmes
échecs préexistants. Les **17 nouveaux tests** de navigation passent ; la sélection
ciblée finale (16 fichiers) passe intégralement. Le typage mobile, le build de types
des bibliothèques et l'export Web final réussissent. Aucun nouvel échec applicatif
n'a été constaté par rapport à la base.

Le typage API reste bloqué par les imports `.ts` / TS5097 préexistants dans
`artifacts/api-server`. Aucun fichier API n'est changé.
